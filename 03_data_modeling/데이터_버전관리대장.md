## 4. 검증 상태

2026-09-03 v03을 기준으로 확인한 결과:

- SQLite 무결성 검사: `ok`
- CSV와 SQLite의 8개 테이블 행 수: 일치
- 각 테이블 PK의 NULL·공백·중복: 0건
- CSV와 SQLite 사이의 PK 집합 차이: 0건
- 추정 FK의 부모 키 매핑 누락: 0건
- `search.total_result_count`와 실제 검색 결과 행 수 차이: 0건
- `search.invalid_stay_date_flag=1`: 9건, 나머지 287건은 0, NULL 0건
- `hotel_click`의 `click_in_result_flag=0`: 2건, 값 1은 229건, NULL 0건
- `hotel_click`이 아닌 이벤트 10,201건의 `click_in_result_flag`: 모두 NULL(적용 대상 아님)
- 알려진 데이터 품질 이슈: `booking_id` `B369bYIG26`, `B4nGXKXBqN`의 예약 호텔은 `H0084`이나 `room_id` `R0196_1`은 `H0196` 소속
- 스키마 주의사항: SQLite에 실제 `FOREIGN KEY` 제약조건은 선언되어 있지 않으므로 적재 시 별도 참조 무결성 검사가 필요함

예약 참조 이슈 2건, 숙박일 역전 9건, 검색결과 미연결 클릭 2건은 원본 생성 기준을
확인하기 전까지 임의 수정하지 않는다. v03의 신규 컬럼은 원천값을 변경하지 않는 분석용 플래그다.

## 5. 새 버전 반영 절차

1. 작업 중인 DB·CSV는 `upload/` 또는 `tmp/`에서 검증한다.
2. 기준 DB에서 모든 업무 테이블의 CSV를 다시 추출한다.
3. DB와 CSV의 테이블별 행 수, PK, 참조 키, 개인정보 잔존 여부를 검사한다.
4. 새 파일에는 같은 기준일·버전·공개 상태를 부여한다.
5. 기존 최신본의 DB·CSV·명세를 `archive/datasets/<기존 기준일_vNN>/`로 이동한다.
6. 새 최신본을 `03_data_modeling/` 바로 아래에 배치한다.
7. 이 대장의 최신본 표, 버전 이력, 행 수와 SHA-256을 갱신한다.
8. `문서_버전관리대장.md`의 분석 데이터 항목을 갱신한다.
9. 관련 파일만 스테이징하고 이동이 Git에서 rename으로 인식되는지 확인한다.

## 6. 파일명 규칙

```text
<테이블명>_YYYY-MM-DD_vNN_<공개상태>.csv
travel_data_filtered_complete_YYYY-MM-DD_vNN_<공개상태>.sqlite
travel_data_filtered_complete_YYYY-MM-DD_vNN_테이블명세.md
```

- DB와 CSV는 같은 스냅샷이면 기준일과 버전을 동일하게 쓴다.
- 공개 가능한 파일은 `비식별`, 원천 보존본은 `원본`으로 표시한다.
- `수정본`, `최종`, `(1)` 대신 버전 번호를 올린다.
- 내용이 바뀌면 반드시 새 버전을 만들고 기존 버전을 덮어쓰지 않는다.
- GitHub에는 비식별 검증을 통과한 데이터만 반영한다.

# 호텔 검색 행동 로그 수집 웹앱 개발 프롬프트

## 1. 역할

너는 15년차 풀스택 개발자이자 데이터 엔지니어다.

내 목표는 실제 여행 예약 사이트처럼 사용자가 호텔을 검색하고, 검색 결과를 탐색하고, 상세 페이지를 열어보고, 뒤로 가고, 검색 조건을 수정하여 재검색하고, 찜하고, 최종적으로 예약하거나 이탈하는 과정을 실험할 수 있는 **호텔 검색 행동 로그 수집용 웹 애플리케이션**을 만드는 것이다.

이 프로젝트의 가장 중요한 목적은 디자인이나 실제 결제 기능이 아니라 **사용자의 검색 의도와 실제 노출 결과, 그리고 이후 행동을 분석할 수 있는 로그 데이터를 정확하게 수집하는 것**이다.

완성 후에는 다음과 같은 사용자 행동 경로를 DB에서 재구성할 수 있어야 한다.

`접속 → 검색 → 검색결과 노출 → 호텔 클릭 → 상세조회 → 뒤로가기 → 필터변경 → 재검색 → 다른 호텔 클릭 → 찜 → 재검색 → 예약`

사용자가 정해진 순서대로 움직이는 것이 아니라 실제 호텔 사이트처럼 자유롭게 탐색할 수 있도록 구현한다.

---

# 2. 기술 스택

개발 난이도와 실행 편의성을 고려하여 다음 기술을 우선 사용한다.

* Backend: Python FastAPI
* Database: SQLite
* ORM: SQLAlchemy
* Frontend: HTML + CSS + JavaScript
* Template: Jinja2
* 데이터 처리: pandas
* 테스트 데이터 생성: Faker 또는 Python
* 실행환경: 로컬 PC
* Python 3.11 이상

과도하게 복잡한 React, Docker, 클라우드 인프라는 사용하지 않는다.

단, 기능 구현상 다른 선택이 명확하게 더 안정적이라면 이유를 설명한 뒤 변경할 수 있다.

---

# 3. 프로젝트의 핵심 목표

웹사이트 사용자의 다음 데이터를 확보해야 한다.

1. 어떤 사용자가 접속했는가
2. 어떤 검색 조건을 사용했는가
3. 검색 조건을 어떻게 변경했는가
4. 몇 번 재검색했는가
5. 각 검색에서 어떤 호텔이 노출됐는가
6. 검색 결과가 몇 건이었는가
7. 각 호텔이 몇 번째 순위로 노출됐는가
8. 어떤 호텔을 클릭했는가
9. 상세페이지에서 얼마나 머물렀는가
10. 상세페이지에서 다시 검색 결과로 돌아갔는가
11. 어떤 호텔을 찜했는가
12. 찜을 취소했는가
13. 필터를 추가하거나 제거했는가
14. 정렬 조건을 변경했는가
15. 어떤 호텔을 예약 단계까지 진행했는가
16. 최종 예약을 완료했는가
17. 예약하지 않고 이탈했는가
18. 한 세션 안에서 사용자가 어떤 순서로 행동했는가

모든 행동은 시간순으로 재구성할 수 있어야 한다.

---

# 4. 기본 데이터 모델

다음 7개 테이블을 핵심 테이블로 사용한다.

## 4-1. USER

사용자 한 명을 나타낸다.

필수 컬럼:

* user_id PK
* user_name
* age
* phone_number
* signup_at

단, 이 프로젝트는 테스트용이므로 실제 개인정보 입력을 강요하지 않는다.

`user_name`은 별명 사용이 가능하도록 하고 `phone_number`는 NULL 허용 또는 테스트용 값만 사용한다.

개인정보 수집이 분석 목적상 불필요하다면 UI에서는 입력을 선택사항으로 처리한다.

---

## 4-2. HOTEL

호텔 마스터 정보다.

필수 컬럼:

* hotel_id PK
* hotel_name
* city_name
* grade
* latitude
* longitude
* hotel_address
* hotel_rating
* accommodation_type

검색 필터 구현에 필요하므로 다음 컬럼도 추가한다.

* price_per_night
* review_count
* amenities_json
* nearest_station
* station_distance_m
* region_name
* thumbnail_url
* description

HOTEL 테이블에 `review_id FK`를 저장하지 않는다.

호텔 1개에 리뷰가 여러 개 존재할 수 있으므로 REVIEW 테이블이 `hotel_id FK`를 가지도록 한다.

---

## 4-3. SEARCH

사용자가 검색 버튼을 한 번 누를 때마다 한 행을 생성한다.

즉:

첫 검색 = 새로운 search_id

필터 변경 후 다시 검색 = 새로운 search_id

지역 변경 후 재검색 = 새로운 search_id

가 되어야 한다.

필수 컬럼:

* search_id PK
* user_id FK
* session_id
* search_time
* query_text
* checkin_date
* checkout_date
* guest_count
* search_region
* sort_condition
* total_result_count
* parent_search_id nullable FK

`parent_search_id`는 재검색 분석을 위해 사용한다.

예:

S001 최초 검색

S002의 parent_search_id = S001

S003의 parent_search_id = S002

이렇게 저장하면 검색 조건 변경 흐름을 추적할 수 있다.

---

## 4-4. SEARCH_FILTER

특정 검색에서 사용한 필터 조건을 저장한다.

필수 컬럼:

* search_filter_id PK
* search_id FK
* accommodation_type
* accommodation_grade
* min_rating
* min_price
* max_price
* amenity_count
* amenities_json
* transport_condition
* region

추가 가능한 조건:

* breakfast_required
* parking_required
* public_bath_required
* free_wifi_required
* max_station_distance_m

SEARCH와 SEARCH_FILTER 사이에 양방향 FK를 만들지 않는다.

다음 구조를 사용한다.

`SEARCH 1 : 1 SEARCH_FILTER`

SEARCH_FILTER.search_id를 FK로 사용한다.

---

# 5. EVENT

이 프로젝트에서 가장 중요한 테이블이다.

사용자의 모든 행동을 이벤트 단위로 저장한다.

필수 컬럼:

* event_id PK
* user_id FK
* session_id
* event_name
* event_time
* search_id nullable FK
* search_filter_id nullable FK
* hotel_id nullable FK
* action_id
* page_name
* event_properties_json

`event_properties_json`에는 이벤트마다 필요한 추가 정보를 JSON 형태로 저장한다.

예:

```json
{
  "rank": 3,
  "previous_page": "search_result",
  "sort": "price_low",
  "result_count": 24
}
```

---

# 6. 반드시 수집해야 하는 EVENT 종류

다음 event_name을 최소한 구현한다.

### 세션

* session_start
* session_end

### 검색

* search_start
* search_submit
* search_result_view
* search_no_result

### 검색 결과 노출

* hotel_impression

검색 결과 화면에 호텔이 노출될 때 호텔별로 이벤트를 남긴다.

예:

search_id = S001

hotel_id = H001

event_name = hotel_impression

event_properties_json:

```json
{
  "rank": 1
}
```

이 데이터를 통해 특정 검색에서 어떤 호텔이 몇 번째 순위에 노출되었는지 분석할 수 있어야 한다.

### 필터

* filter_open
* filter_change
* filter_add
* filter_remove
* filter_apply
* filter_reset

필터 변경 이벤트에는 반드시

* previous_value
* new_value
* filter_name

을 저장한다.

예:

```json
{
  "filter_name": "max_price",
  "previous_value": 200000,
  "new_value": 150000
}
```

### 정렬

* sort_change

예:

```json
{
  "previous_sort": "recommended",
  "new_sort": "rating_high"
}
```

### 호텔 탐색

* hotel_click
* hotel_detail_view
* back_to_results

### 찜

* wishlist_add
* wishlist_remove

별도 Wishlist 테이블을 만들지 않고 우선 이벤트로 기록한다.

필요하면 추후 별도 테이블로 확장할 수 있도록 구현한다.

### 예약

* booking_start
* booking_complete
* booking_cancel

### 리뷰

* review_view
* review_submit

### 기타

* page_view
* exit

---

# 7. REVIEW

필수 컬럼:

* review_id PK
* hotel_id FK
* user_id FK
* rating
* review_created_at
* review_text
* review_image

호텔 상세 페이지에서 리뷰 목록을 볼 수 있게 한다.

테스트 사용자가 리뷰를 작성할 수도 있도록 구현한다.

# 8. RESERVATION

예약 정보는 다음 구조로 수정한다.

* reservation_id PK
* user_id FK
* hotel_id FK
* search_id FK
* reservation_status
* total_price
* reservation_created_at
* checkin_date
* checkout_date
* guest_count
* room_count

`user_id`를 PK로 사용하지 않는다.

`reservation_id`가 PK다.

한 사용자가 여러 예약을 할 수 있기 때문이다.

# 9. 세션 관리

사용자가 사이트에 접속하면 자동으로 고유한 `session_id`를 생성한다.

예:

`SES_20260826_A8F12C`

같은 브라우저에서 사이트를 탐색하는 동안 동일한 session_id를 유지한다.

한 세션 안에서 여러 번 검색할 수 있어야 한다.

예:

```text
session_id = SES001

SEARCH001
↓
호텔 상세
↓
뒤로가기
↓
필터 수정
↓
SEARCH002
↓
호텔 상세
↓
찜
↓
SEARCH003
↓
예약
```

이 전체 행동을 하나의 session_id로 묶을 수 있어야 한다.

# 11. 검색 결과 화면

호텔 검색 결과를 카드 형태로 표시한다.

카드에는 최소:

* 호텔 사진
* 호텔 이름
* 지역
* 1박 가격
* 평점
* 리뷰 수
* 호텔 등급
* 숙소 유형
* 역과의 거리
* 주요 편의시설
* 찜 버튼
* 상세보기 버튼

을 표시한다.

검색 결과 화면에서는 다음 기능을 제공한다.

* 필터 변경
* 가격순 정렬
* 평점순 정렬
* 추천순 정렬
* 호텔 상세보기
* 찜
* 검색 조건 변경
* 재검색

사용자가 검색 결과 페이지를 볼 때 노출된 호텔별 `hotel_impression` 로그를 남긴다.

동일 화면 렌더링 때문에 동일 호텔 impression 이벤트가 불필요하게 중복 생성되지 않도록 한다.

# 13. 예약 화면

예약하기를 누르면 바로 예약 완료시키지 않는다.

다음 단계로 구성한다.

### 1단계

예약하기

→ `booking_start`

### 2단계

예약 정보 확인

* 호텔
* 체크인
* 체크아웃
* 투숙 인원
* 객실 수
* 총 금액

### 3단계

`예약 확정`

→ RESERVATION 생성

→ `booking_complete`

실제 결제 기능은 구현하지 않는다.

# 14. 검색 로직

HOTEL 테이블 데이터를 기반으로 실제 검색 결과가 달라져야 한다.

예:

사용자 검색조건:

* Tokyo
* 100,000원 이하
* 평점 8.0 이상
* 대욕장 있음

조건을 만족하는 호텔만 결과로 표시한다.

필터가 변경되면 검색 결과도 실제로 변경되어야 한다.

정렬 기능도 실제 데이터에 반영한다.

# 15. 호텔 테스트 데이터

최소 150개 이상의 가상 일본 호텔 데이터를 생성한다.

도시는 최소 다음을 포함한다.

* Tokyo
* Osaka
* Kyoto
* Fukuoka
* Sapporo

각 호텔은 서로 다른:

* 가격
* 등급
* 평점
* 숙소 유형
* 편의시설
* 역 거리
* 리뷰 수

를 가지도록 한다.

분석 실험을 위해 특정 조건에서는 검색 결과 적합도가 높고 특정 조건에서는 낮아질 수 있도록 데이터 분포를 다양하게 만든다.

테스트 데이터가 지나치게 균등하게 생성되지 않도록 한다.

# 16. 데이터 분석 목적

최종 DB 데이터를 이용하여 다음 질문을 분석할 수 있어야 한다.

### 검색 행동

* 사용자당 검색 횟수
* 세션당 검색 횟수
* 재검색률
* 검색 조건 변경률
* 필터 사용률

### 검색 결과

* 검색당 결과 수
* 검색 결과 없음 비율
* 호텔별 노출 횟수
* 평균 노출 순위

### 탐색 행동

* 검색 → 상세조회 전환율
* 상세조회 → 뒤로가기 비율
* 검색 → 찜 전환율
* 검색 → 예약 전환율

### 이탈

* 검색 후 아무 행동 없이 종료
* 상세조회 후 뒤로가기
* 여러 번 재검색 후 종료
* 찜 후 종료
* 예약 단계 중 이탈

### 핵심 분석

다음 가설을 분석할 수 있어야 한다.

> 검색 의도와 실제 노출 호텔의 적합도가 낮을수록 검색 결과 이탈률과 재검색률이 높아질 것이다.

따라서 반드시 다음 연결이 가능해야 한다.

`USER`

→ `SESSION`

→ `SEARCH`

→ `SEARCH_FILTER`

→ `HOTEL IMPRESSION`

→ `EVENT`

→ `RESERVATION`

# 20. 데이터 무결성

다음을 반드시 지킨다.

* 모든 PK는 유일해야 한다.
* FK 관계를 정확하게 설정한다.
* 동일 검색에 해당하는 event는 동일 search_id를 가진다.
* 재검색하면 새로운 search_id를 만든다.
* 동일 세션이면 session_id는 유지한다.
* 예약에는 예약을 발생시킨 search_id를 저장한다.
* hotel_impression에는 hotel_id와 search_id를 반드시 저장한다.
* event_time은 millisecond 수준까지 저장 가능한 datetime 형태를 사용한다.
* 실제 DB 저장 성공 이후 사용자 화면을 업데이트한다.

# 21. 중복 및 잘못된 관계 수정 원칙

기존 초안에는 일부 중복 또는 순환 FK가 존재할 수 있다.

다음 원칙으로 수정한다.

### SEARCH

체크인 날짜가 중복되어 있으면 `checkin_date` 하나만 사용한다.

### SEARCH ↔ SEARCH_FILTER

두 테이블이 서로 FK를 가지는 순환 구조를 만들지 않는다.

`SEARCH_FILTER.search_id → SEARCH.search_id`

구조를 사용한다.

### HOTEL ↔ REVIEW

HOTEL에 review_id를 저장하지 않는다.

`REVIEW.hotel_id → HOTEL.hotel_id`

구조를 사용한다.

### RESERVATION

reservation_id가 PK다.

user_id와 hotel_id는 FK다.

# 28. 구현 진행 방법

한 번에 설명만 하고 끝내지 말고 실제 프로젝트 파일을 생성하고 코드를 구현하라.

진행 순서는 다음과 같이 한다.

### Phase 1

현재 요구사항을 분석하고 DB ERD 및 폴더구조를 확정한다.

### Phase 2

DB 모델과 샘플 데이터를 구현한다.

### Phase 3

사용자 등록 및 세션 추적을 구현한다.

### Phase 4

호텔 검색 / 필터 / 정렬을 구현한다.

### Phase 5

검색 결과 / 상세페이지 / 뒤로가기를 구현한다.

### Phase 6

찜 / 리뷰 / 예약 기능을 구현한다.

### Phase 7

EVENT Tracking을 모든 주요 행동에 연결한다.

### Phase 8

관리자 로그 확인 페이지와 CSV export를 구현한다.

### Phase 9

테스트 시나리오를 실행하고 오류를 수정한다.

### Phase 10

README를 완성한다.

각 Phase 이후 실제 코드 상태를 점검하고 다음 단계로 진행한다.

# 29. 중요 개발 원칙

내가 중간에 코드를 직접 작성해야 하는 방식으로 진행하지 않는다.

가능한 작업은 네가 직접:

* 파일 생성
* 코드 작성
* DB 생성
* 테스트
* 오류 수정
* 실행 검증

까지 수행한다.

오류가 발생하면 단순히 오류 내용을 나에게 전달하지 말고 우선 원인을 분석하고 직접 수정한다.

기능을 구현했다고 가정하지 말고 실제 테스트 결과를 확인한다.

기존 코드가 정상 작동하면 불필요하게 전체 코드를 다시 작성하지 않는다.

중요한 수정 전에는 관련 파일을 먼저 확인한다.

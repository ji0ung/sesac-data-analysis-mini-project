# SQLite 44.719 MiB 경량화 재현 가이드 — AI 실행용

## 목적

이 문서는 호텔검색 관측형 합성 1,000명 SQLite 원본을 **분석·공유용 44.719 MiB 구조**로 재현할 때 사람과 AI가 따라야 할 실행 계약이다.

- 입력 기준: 93.363 MiB 원본 SQLite
- 출력 기준: 44.719 MiB 분석·공유용 SQLite
- 실행 스크립트: `공통스크립트/sqlite_optimize_44mib.py`
- 원본은 절대 수정하거나 덮어쓰지 않는다.
- 14.297 MiB 사전 매핑 테스트본은 이 절차의 대상이 아니다.

## 승인된 변환 범위

다음 변경만 허용한다.

1. 업무 테이블 8개만 새 DB로 복사한다.
   - `booking`
   - `event`
   - `hotel`
   - `room`
   - `search`
   - `search_filter`
   - `search_result`
   - `user`
2. `_generation_metadata`를 출력에 복사하지 않는다.
3. 모든 사용자 정의 인덱스와 `TEXT PRIMARY KEY` 제약을 출력에 만들지 않는다.
4. 8개 업무 테이블의 `data_origin` 컬럼을 출력에서 제거한다.
5. 다음 시간 컬럼의 값 끝에 있는 정확한 문자열 ` KST`만 제거한다.
   - `event.event_at`
   - `event.session_end_time`
   - `search.search_time`
   - `user.signup_at`
6. SQLite 페이지 크기를 16,384 bytes로 설정하고 최종 `VACUUM`을 실행한다.
7. 다음 전부 NULL 컬럼은 삭제하지 않는다.
   - `event.review_completed_at`
   - `event.review_text`
   - `search_filter.property_type`
   - `search_filter.property_grade`
   - `user.age_group`

그 밖의 값, 행, 컬럼명, 컬럼 순서, SQLite 자료형은 변경하지 않는다.

## 중요한 의미 변화

- 출력 DB에는 PK·UNIQUE 제약과 업무 조회용 인덱스가 없다.
- ID 컬럼은 남아 있어 JOIN은 가능하지만 SQLite가 중복과 NULL을 막아주지 않는다.
- 시간 문자열은 시간대 표기가 없어도 **KST 로컬 시각**으로 해석한다.
- `data_origin`이 필요하면 원본 DB 또는 외부 실행 매니페스트에서 확인한다.
- 출력 DB는 읽기·분석·공유용이다. 데이터 추가·수정과 10,000명 증강 입력에는 원본 또는 제약·인덱스가 있는 버전을 사용한다.

## 실행 전 확인

AI는 실행 전에 다음 조건을 확인한다.

- 입력 파일이 실제 파일인지 확인한다.
- 입력과 출력 경로가 서로 다른지 확인한다.
- 출력 파일이 존재하지 않는지 확인한다.
- 입력 DB에 8개 업무 테이블과 각 `data_origin` 컬럼이 있는지 확인한다.
- 사용자가 명시하지 않았다면 기존 파일을 삭제하거나 덮어쓰지 않는다.
- 입력 경로에 공백이나 한글이 있어도 경로 전체를 따옴표로 감싼다.

알려진 원본 SHA-256은 다음과 같다.

```text
db80db7048add9c0c4cb1a985e67a77ae99bef3a30ce32bedb70cc0ee61dc896
```

스크립트는 다른 호환 입력도 처리할 수 있지만, 해시가 다르면 알려진 원본과 다른 파일이라는 사실을 검증 JSON에 기록한다.

## AI에게 내릴 명령문

## 자동 검증 계약

스크립트는 생성 후 다음을 모두 검사한다.

| 검사 | 통과 조건 |
|---|---|
| 원본 불변 | 실행 전후 원본 SHA-256 동일 |
| 업무 테이블 | 출력에 정확히 8개 존재 |
| 행 수 | 테이블별 원본과 출력 동일 |
| 값 보존 | `data_origin` 제외·` KST` 제거 후 행 단위 SHA-256 동일 |
| 인덱스 | 사용자 인덱스 0개 |
| PK | PK 컬럼 0개 |
| 반복 컬럼 | `data_origin` 위치 0개 |
| 시간 축약 | 대상 열의 ` KST` 잔존 0건 |
| NULL 컬럼 | 지정한 5개 컬럼 모두 존재 |
| 페이지 크기 | 16,384 bytes |
| 빈 페이지 | `freelist_count=0` |
| 무결성 | `PRAGMA integrity_check=ok` |

하나라도 실패하면 종료 코드는 1이며 출력 SQLite를 삭제한다. 검증 JSON이 만들어진 뒤 최종 검증에서 실패한 경우 JSON은 원인 확인을 위해 남길 수 있다.

## 알려진 기준 결과

기준 원본을 같은 환경에서 처리한 알려진 결과는 다음과 같다.

- 출력 크기: 46,891,008 bytes
- 출력 크기: 44.719 MiB
- 페이지 크기: 16,384 bytes
- 페이지 수: 2,862
- freelist: 0
- 사용자 인덱스: 0
- PK 제약 컬럼: 0

SQLite 라이브러리 버전과 페이지 배치 차이 때문에 호환 입력의 파일 바이트 크기나 파일 전체 SHA-256은 달라질 수 있다. 판정의 우선순위는 파일 크기가 아니라 **행 수, 변환 후 값 해시, 무결성 검사**다.

### 2026-09-07 재현 시험

현재 Windows/Python SQLite 환경에서 기준 원본으로 스크립트를 실행한 결과는 다음과 같다.

- 검증 상태: `PASS`
- 출력 크기: 46,759,936 bytes (44.593750 MiB)
- 페이지 수: 2,854
- 기준 44.719 MiB 파일보다 8페이지 작지만, 8개 테이블의 행 수와 허용 변환 후 전체 값 해시는 모두 일치했다.
- 원본 SHA-256은 실행 전후 동일했다.
- `integrity_check=ok`, `freelist_count=0`, 사용자 인덱스 0개, PK 컬럼 0개를 확인했다.

따라서 문서의 “44.719 MiB”는 승인된 구조를 식별하는 기존 파일명·기준값으로 사용하며, 재현 출력은 SQLite 버전과 페이지 배치에 따라 약간 더 작아질 수 있다.

## AI 작업 규칙

AI가 이 작업을 수행할 때 다음을 지킨다.

1. 기존 DB를 직접 열어 수정하지 않는다.
2. 기존 출력 파일이 있으면 자동 삭제하지 않는다.
3. 스키마가 다르면 컬럼을 추측하지 않고 중단한다.
4. 누락된 컬럼이나 테이블을 임의로 생성하지 않는다.
5. 시간 값의 숫자 부분이나 시간대를 변환하지 않는다.
6. 전부 NULL인 5개 컬럼을 최적화 대상으로 제거하지 않는다.
7. 생성 완료 후 검증 JSON의 `status`가 `PASS`인지 확인한다.
8. 사용자에게 출력 경로, 크기, SHA-256, 원본 불변 여부를 보고한다.
9. 14.297 MiB 사전 매핑 구조를 이 스크립트에 섞지 않는다.
10. 운영·증강용으로 사용할지 묻는 경우 이 결과는 읽기·분석·공유용이라고 설명한다.

## 실패 시 처리

- `data_origin이 없다`: 이미 경량화된 DB이거나 입력 버전이 다르므로 원본을 다시 확인한다.
- `출력 파일이 이미 있다`: 새 출력 이름을 사용한다.
- `필수 테이블이 없다`: 테이블명을 추측하지 말고 입력 DB를 진단한다.
- `projected_values_exact=false`: 출력물을 사용하지 말고 테이블별 해시 불일치를 확인한다.
- `integrity_ok=false`: 출력물을 폐기하고 저장 공간·입력 파일 상태를 점검한다.
- 알려진 크기와 다르지만 모든 필수 검사가 PASS이면 SQLite 버전과 페이지 배치 차이를 기록한다.

# 호텔 검색 2단계 — 관측형 합성 1,000명 파일럿 Codex 실행 프롬프트

> **상태: `SUPERSEDED_DO_NOT_RUN`**  
> 이 버전은 보존용이다. 실행하지 말고 개정 버전 02를 사용한다.

## 1. 선행조건과 사용 방법

이 파일은 일본 호텔 검색 프로젝트의 **2단계: 관측형 합성 사용자 1,000명 파일럿 생성 → 1단계 분석 재실행 → 원본 대비 QA**를 위한 Codex용 프롬프트다.

이 프롬프트를 작성하는 데는 1단계 결과가 없어도 되지만, **실제 2단계 실행에는 1단계 결과가 반드시 필요하다.** 아래 프롬프트는 1단계 산출물이 없거나 검증에 실패하면 합성 데이터 생성 전에 중단하도록 설계되어 있다.

이번 2단계에 포함되지 않는 작업:

- 10,000명 본 생성
- 0건 즉시 이탈 2%·5%·10% 스트레스 세트
- 희소집단 과표집 세트
- S1 인접 지역, S2 필터 완화, S3 통합 제품 시나리오
- 예약률 가정을 사용한 BOOKING 생성

권장 실행 방법:

1. 원본·기준 문서와 1단계 산출물을 동일한 Codex 작업공간에 준비한다.
2. 전체를 한 번에 맡기려면 `2. 통합 실행 프롬프트`를 사용한다.
3. 생성 설정과 QA를 단계별로 확인하려면 `3~7. 단계별 프롬프트`를 순서대로 사용한다.
4. 1단계 사전 게이트가 통과하기 전에는 단계별 프롬프트 2 이후를 실행하지 않는다.

## 2. 통합 실행 프롬프트

```text
당신은 합성 데이터 설계자이자 데이터 분석 QA 엔지니어다. 일본 호텔 검색 프로젝트의 2단계를 수행하라. 2단계의 목적은 원본 296건에서 발견한 구조·분포·행동 관계를 재현하는 “관측형 합성 1,000명 파일럿”을 만들고, 1단계와 동일한 분석 코드로 다시 분석하여 생성기가 정상인지 검증하는 것이다.

첨부 표시명과 실제 로컬 파일명이 다를 수 있으므로 `rg --files` 등으로 경로를 찾아 명시적으로 매핑한다. 경로를 생성 코드에 하드코딩하지 않고 명령행 인수 또는 설정으로 받는다.

[근거 우선순위]

- 문서에 적힌 숫자를 합성 목표로 직접 복사하지 말고 1단계 결과 파일과 코드에서 불러온 기준값을 사용한다.

[0. 사전 실행 게이트 — 가장 먼저 수행]
다음을 확인하기 전에는 생성기 코드를 실행하지 않는다.

1. 원본 SQLite와 1단계 코드·Excel·Word·실행기록이 모두 존재한다.
2. 네 개의 1단계 산출물이 동일 실행 묶음인지 확인된다.
3. 1단계 실행기록의 원본 SHA-256이 현재 `travel_data_filtered_complete_2026-09-03_v02_비식별(1).sqlite`와 일치한다.
4. 1단계 최종 상태가 PASS 또는 처리방안이 명시된 조건부 PASS다.
5. 다음 기준이 코드·Excel·Word에서 서로 일치한다: SEARCH 296, 검색 세션 43, 0건 검색 147, 0건→다음 검색 전이 140, 세션 세그먼트 합 43.
6. A1 부분 채택, A3 제외, B2 비인과, hotel_click 단일 상세진입 지표, BOOKING 참고 처리 원칙이 반영돼 있다.
7. 미해결 오류가 생성 규칙을 바꿀 정도로 중대하지 않거나, 생성 시 처리방안이 명시되어 있다.

게이트 실패 시:
- 합성 데이터·생성기 실행·설정 동결을 하지 않는다.
- `호텔검색_2단계_진입점검_[RUN_TS]_01.md`만 작성한다.
- 누락 파일, 불일치 값, 필요한 1단계 재실행 항목을 정확히 적고 사용자에게 보고한 뒤 종료한다.

알려진 조건부 이슈의 기본 처리:
- checkin_date/checkout_date 역전 행은 원본을 고치지 않고 합성 시 유효한 체류기간만 재표본한다.
- 클릭 호텔이 SEARCH_RESULT에 없는 원본 경로는 합성기에 복제하지 않는다. 모든 클릭은 노출 결과 중에서만 선택한다.
- BOOKING–ROOM 호텔 불일치는 S0에서 BOOKING을 생성하지 않아 전파하지 않는다.
- ROOM은 물리 객실 한 칸이 아니라 객실 상품/타입으로 해석한다. 물리 재고·이중예약 분석은 이번 범위가 아니다.

[1. 기준값·설정 동결]
- 1단계 Python 코드를 원본 DB에 다시 실행하여 기준 결과를 별도 폴더에 재현한다.
- 1단계 Excel에서 지표명, 분석 단위, 분자, 분모, 비율, 세그먼트 정의를 읽어 `baseline_metrics`로 만든다.
- 원본 기준을 코드에 숫자로 중복 하드코딩하지 않는다. 다만 데이터 버전 확인용 최소 assertion은 허용한다.
- 다음 설정을 JSON 또는 YAML에 기록한다.
  · sample_set_type=`observed_like`
  · scenario_id=`S0`
  · sample_design_id=`OBSERVED_BOOTSTRAP_296_V01`
  · config_version=`S0_PILOT_V01`
  · generation_version=`01`
  · random_seed=`20260903`를 기본값으로 사용하되, 이미 승인된 seed가 1단계 기록에 있으면 그 값을 우선한다.
  · n_users=1000, n_sessions=1000
  · source_db_sha256, stage1_code_sha256, stage1_result_sha256
- 하나의 고정 seed를 사용한다. QA를 통과하기 위해 seed만 반복 변경하는 것을 금지한다.

[2. 생성 원칙]
- 결과 세그먼트를 628명·233명·93명·47명처럼 먼저 할당하지 않는다.
- USER 성향 → 탐색지속성 → 검색 행동·필터 → 결과 없음/있음 → 노출 결과 → 클릭·후속 행동 → 생성 후 세그먼트 산출 순으로 만든다.
- `탐색지속성`은 검색 결과보다 먼저 생성한다. 0건이 발생한 뒤 검색 횟수를 강제로 더하는 B2 인과 규칙은 사용하지 않는다.
- 첫 검색은 원본 첫 검색의 지역×의도×필터 결합분포에서 생성한다.
- 재검색은 직전 검색을 복사한 뒤 원본 전이에서 관측된 방식으로 1~2개 항목만 변경한다. 매 검색마다 모든 값을 독립 재추출하지 않는다.
- 지역과 검색의도를 독립 확률로 분리하지 말고 결합분포를 보존한다.
- 희소 셀은 그대로 확대해 새로운 사실처럼 만들지 않는다. 최소 셀 크기 규칙과 상위 집단으로의 풀링 또는 평활화 규칙을 config에 기록한다.
- H3의 재검색 유형별 성공률을 고정 성공확률로 박지 않는다. H3는 생성 후 방향을 확인하는 탐색적 QA 항목이다.
- 0건 즉시 이탈은 S0에서 생성하지 않는다. 첫 검색이 0건인 세션에는 적어도 한 번의 후속 검색이 있어야 한다.
- 관측형과 원본을 한 DB·한 표본으로 합치지 않는다.

[3. 테이블별 생성]

A. USER
- 합성 사용자 1,000명만 생성한다. 원본 USER 89명을 복제·추가하지 않는다.
- user_id는 원본과 충돌하지 않는 결정적 합성 키를 사용한다.
- age_group과 signup_at은 원본 USER의 유효 분포에서 생성하되 범위를 벗어나지 않는다.
- user_name은 `합성사용자_000001` 같은 비식별 값, email은 `synthetic000001@example.invalid` 같은 무효 도메인을 사용한다.
- 사용자별 exploration_persistence를 결과 전에 생성한다. 원본 세션 검색 횟수 분포와 연결하되 결과 세그먼트와 같은 변수가 아님을 명시한다.
- 검색 성향은 필요한 경우 다중 라벨로 저장하고 결과 세그먼트와 분리한다. 제외된 C3 품질 우선 사용자 세그먼트를 만들지 않는다.

B. HOTEL·ROOM
- 원본 HOTEL 1,000행과 ROOM 3,000행을 값 변경 없이 복사한다.
- HOTEL 또는 ROOM 신규 행을 생성하지 않는다.
- ROOM.room_id가 소속 HOTEL.hotel_id와 일치하도록 모든 결과 연결을 검증한다.
- ROOM은 객실 상품/타입으로 데이터 사전에 고정한다.

C. SEARCH
- 합성 사용자당 검색 세션 1개를 생성하여 1,000개의 고유 session_id를 만든다.
- 세션별 검색 횟수는 원본 43세션의 분포와 탐색지속성을 사용해 생성한다. 모두 7회로 고정하지 않는다.
- 원본 참고치인 평균 약 6.88회, 범위 1~31회는 QA 기준이며 강제 행 수가 아니다.
- 예상 SEARCH는 약 6,884행이지만 실제 수는 생성 결과로 결정한다.
- search_time은 세션 내 엄격한 시간순으로 생성한다. 동률이 필요하면 search_id로 안정 정렬 가능하게 한다.
- checkin_date<checkout_date, guest_count 유효 범위를 강제한다.
- query_text의 NULL은 정상 destination 검색일 수 있으므로 오타로 취급하지 않는다.
- data_origin, sample_set_type, scenario_id, random_seed, config_version, generation_version 추적정보를 합성 행동행에 남긴다.

D. SEARCH_FILTER
- SEARCH 1행당 SEARCH_FILTER 1행을 생성한다.
- price는 원본 이산분포, user_rating_min은 원본 설정값 분포, amenity_count는 원본 범위·분포를 사용한다.
- 첫 검색은 지역×의도×필터 결합분포를 사용한다.
- 후속 검색은 직전 조건에서 동일조건 반복, 조건 완화, 검색어 수정, 지역 변경, 조건 강화, 혼합 변경의 전이 구조를 사용한다.
- 가격 상한 증가·해제, 최소평점 감소·해제, amenity_count 감소는 완화이며 반대는 강화다.
- property_type·property_grade 등 원본에서 모두 결측인 필드를 임의로 채워 새 신호를 만들지 않는다.

E. 결과 없음과 SEARCH_RESULT
- 0건 여부는 SEARCH·FILTER의 제한 수준, 지역·의도, 세션 위치와 탐색지속성을 바탕으로 평활화된 관측 모델에서 발생시킨다.
- 모델은 계층적 경험확률/Beta 평활화 또는 규제된 확률모형 중 표본 크기에 더 안정적인 방법을 선택하고 이유를 기록한다.
- A1 방향은 보존하되 A3 오타 변수는 사용하지 않는다.
- 0건이면 total_result_count=0이고 SEARCH_RESULT는 0행이다.
- 비0건이면 원본의 양수 total_result_count 실측분포를 재표본한다. 검색당 결과를 24~25개로 고정하지 않는다.
- 원본 참고 분포는 양수 검색 평균 약 57.4, 중앙값 20, 최대 1,000이며 목표를 강제하지 않는다.
- 결과 후보는 기존 HOTEL·ROOM에서만 고른다. 지역, 평점, 가격, 인원 등 실제 컬럼으로 검증 가능한 조건은 충족시킨다.
- amenity_count와 실제 옵션의 직접 대응이 데이터 사전에 없으면 임의의 편의시설명을 만들지 말고 제한 수준 모델에만 사용하거나 근거 있는 room_options 파싱 규칙을 문서화한다.
- 목표 결과 수가 적격 후보 수를 넘으면 후보 수로 제한하고 `candidate_cap_applied`를 기록한다. 제한 발생률이 높으면 QA 이슈로 보고한다.
- 같은 search_id에서 hotel_id를 중복 노출하지 않는다.
- 각 결과의 room_id는 같은 hotel_id 소속이어야 한다.
- result_rank는 1부터 결과 수까지 중복 없이 생성하고, result_score·price_rank 규칙을 기록한다.
- SEARCH.total_result_count와 실제 SEARCH_RESULT 행 수를 검색별로 일치시킨다.

F. EVENT
- EVENT는 독립 난수 테이블로 만들지 않고 USER→SEARCH→SEARCH_RESULT에서 파생한다.
- 각 합성 세션에 session_start와 session_end를 1건씩 생성한다.
- SEARCH 1행당 search_submit 1건을 생성한다.
- SEARCH_RESULT 1행당 hotel_impression 1건을 생성한다.
- hotel_click가 발생하면 해당 검색에 실제 노출된 호텔만 선택하고 같은 키의 hotel_detail_view를 동반 생성한다.
- room_option_view·room_select 등은 앞선 노출·클릭·상세 경로와 시간순서가 맞을 때만 생성한다.
- 시간순서는 session_start ≤ search_submit ≤ impression ≤ click ≤ detail ≤ room option/select ≤ session_end다.
- 모든 EVENT의 user_id는 해당 session_id의 한 사용자와 일치해야 한다.
- experiment_assignment와 제품 시나리오 이벤트는 S0에서 만들지 않는다.
- booking_start, booking_complete, booking_cancel 등 예약 이벤트는 S0에서 만들지 않는다.
- session_end_time은 해당 세션의 최대 event_at 이상이어야 한다.

G. BOOKING
- 원본 스키마는 유지하되 S0 관측형 파일럿의 BOOKING은 0행으로 둔다.
- 원본 36/296 비율을 확대 적용하지 않는다.
- 예약 생성은 별도 승인된 후속 시나리오의 범위임을 metadata에 기록한다.

H. 추적 메타데이터
- 합성 행동 테이블에는 가능한 범위에서 data_origin=`synthetic_augmentation`, sample_set_type=`observed_like`, scenario_id=`S0`, random_seed, config_version, generation_version를 기록한다.
- `_generation_metadata` 테이블을 만들어 source 파일명·SHA-256, 생성시각 KST, 코드·config 해시, 행 수, seed, 생성 버전, known limitations를 저장한다.
- 원본 기준정보인 HOTEL·ROOM의 data_origin은 임의로 synthetic으로 바꾸지 않는다.

[4. 생성 직후 구조·행동 QA]

G1 구조 — 하나라도 실패하면 파일럿 FAIL
```

## 4. 단계별 프롬프트 2 — 생성 설계와 config 확정


## 6. 단계별 프롬프트 4 — 동일 분석 재실행 및 원본–합성 QA

```text
G1 구조, G2 행동순서, G5 분리를 통과한 관측형 1,000명 DB에만 수행하라.

핵심 ±3%p:
- 전체 결과 없음률
- 0건 후 후속검색률
- 즉시 회복률
- 세션 최종 회복률
- hotel_click 기준 상세진입률
- 직접 성공·결과 노출 미선택·재검색 회복·지속 실패의 각 세션 비율

기타 ±5%p:
- 지역·의도 구성과 0건률
- 가격·최소평점·편의시설 설정 분포
- 재검색 유형 구성 및 결과. 희소 셀은 n·방향 중심으로 별도 표시

연속형은 세션당 검색 수, 검색 간격, 양수 결과 수의 평균·중앙값·사분위·최대·ECDF를 비교하되 임의 허용오차로 PASS/FAIL을 만들지 않는다.

핵심 허용오차 실패 시 seed를 바꾸거나 행을 직접 수정하지 말고 config의 생성 규칙을 수정해야 한다.
```

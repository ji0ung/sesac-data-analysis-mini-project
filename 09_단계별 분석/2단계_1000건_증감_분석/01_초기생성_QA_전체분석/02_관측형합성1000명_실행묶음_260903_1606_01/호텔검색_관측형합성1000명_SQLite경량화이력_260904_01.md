### 8.2 실제 적용한 방법

#### 고정 형식 문자열 ID를 정수로 저장

ID의 접두사·구분자·숫자 자릿수가 일정한지 전체 값을 확인한 뒤 숫자 부분을 정수로 저장했다. 조회 뷰에서 `printf`, `substr` 등을 사용해 접두사와 앞자리 0까지 복원한다. 고유 ID마다 별도의 긴 매핑 문자열을 저장하는 방식은 사용하지 않았다.

- 예: `SYN_E0001_00001` → 정수 `100001` → 조회 시 `SYN_E0001_00001`
- 적용: `event`의 이벤트·호텔·검색 ID, `hotel`의 호텔 ID, `room`의 객실·호텔 ID, `search`의 검색·세션 ID, `search_filter`의 필터·검색 ID, `search_result`의 결과·검색·객실 ID, `user`의 사용자 ID
- 이 규칙은 해당 입력 데이터의 형식을 기준으로 한다. 다른 형식의 ID를 추가하려면 변환 규칙을 다시 검토해야 한다.

#### 반복 문자열을 사전 테이블로 분리

같은 문자열을 각 행에 반복 저장하는 대신 `_dict_*`에 한 번 저장하고, 업무 데이터에는 정수 코드를 저장했다. 사전과 코드의 예상 저장량이 원문 반복 저장보다 작은 열에 적용했다.

| 원래 테이블 | 사전으로 분리한 열 |
|---|---|
| `event` | `event_type`, `event_at`, `device` |
| `hotel` | `actual_data_sources` |
| `room` | `room_options`, `room_type` |
| `search` | `query_text`, `checkin_date`, `checkout_date`, `sort_option`, `destination` |
| `search_filter` | `region` |

예를 들어 `event_type`은 24종류가 238,851행에 반복된다. 문자열 자체만 약 3.67 MiB였으므로 작은 사전 테이블을 추가하더라도 전체 공간이 줄어든다. 시간 문자열도 원래 값을 사전에 보관하므로 이번 단계에서는 시각이나 시간대 표현을 추가로 변경하지 않았다.

#### 세션 공통 정보를 한 번만 저장

`event`에서 반복되던 `session_id`, `user_id`, `session_end_time`을 `_sessions` 1,000행으로 분리했다. 이벤트에는 `_session_ref`와 NULL 상태를 보존하는 `_user_present`, `_end_present`를 저장했다.

세션별 사용자와 종료 시각에 서로 다른 비NULL 값이 없는지 확인했다. 종료 시각이 일부 이벤트에서만 NULL인 경우도 뷰에서 원래 NULL을 그대로 복원한다.

#### 관계·명명 규칙으로 복원 가능한 중복 ID 제거

- `event.search_filter_id`: 모든 행에서 `search_id`의 `SYN_Q`를 `SYN_F`로 바꾼 값과 일치하고 NULL 상태도 같음을 검증했다. 물리 열을 제거하고 뷰에서 복원한다.
- `search_result.hotel_id`: 객실 테이블과의 관계가 전 행에서 일치함을 확인했다. 또한 객실 ID `R0252_1`의 호텔 ID가 `H0252`인 명명 규칙을 객실 전체에서 검증했다. 최종 뷰에서는 객실 정수 ID로 호텔 ID를 직접 복원하므로 이 열을 위해 객실 테이블을 매번 조인하지 않는다.
- `result_rank`와 `price_rank`는 194,838행에서 값이 달라 모두 유지했다.

### 8.3 테이블과 뷰가 늘어도 작아지는 이유

물리 테이블 `_data_*`는 정수와 중복을 줄인 데이터를 저장한다. `_dict_*`와 `_sessions`는 반복되던 값을 한 번씩 보관한다. 기존 이름의 뷰 8개는 이 정보를 원래 열과 값으로 보여주는 SQL 정의이며, 조회 결과 전체를 별도로 저장하지 않는다.

따라서 객체 개수는 증가해도 전체 저장 바이트는 감소한다. SQLite의 일반 문자열 열은 같은 문자열이 반복된다고 자동으로 하나만 저장하지 않는다. 다만 짧거나 대부분 고유한 문자열은 사전 분리의 효과가 작거나 오히려 공간을 늘릴 수 있다.

### 8.4 인덱스의 정확한 상태

- 추가 경량 테스트본에는 `_data_room(room_id)`에 대한 명시적 UNIQUE 인덱스 `_room_key` 1개가 있다.
- 사전 테이블과 `_sessions`의 `id INTEGER PRIMARY KEY`는 내부 rowid를 활용하며, 별도의 TEXT 기본키 자동 인덱스를 만드는 구조와 다르다.
- 기존의 이벤트·검색 결과용 보조 인덱스는 복원하지 않았다.
- `_room_key`는 최종 `search_result` 뷰의 호텔 ID 복원에는 필요하지 않다. 해당 뷰는 검증된 ID 형식으로 직접 복원한다.
- 이번 추가 절감의 핵심은 인덱스 삭제가 아니라 ID 정수화와 반복값·관계 중복 제거다.

### 8.5 검증 결과와 범위

생성 스크립트 `sqlite_compact_lossless.py`는 입력 8개 테이블과 출력의 동일 이름 뷰를 전체 행 단위로 비교했다. 모든 열의 값과 NULL이 일치했으며 행 수는 4절의 표와 동일하다. 로컬 검증 결과는 추가 경량 테스트본과 같은 이름의 `.verification.json`에 저장했다.

- 8개 업무 데이터셋 전체: `verified_exact = true`
- 전부 NULL인 5개 열: 기존 이름의 뷰에서 그대로 유지
- `PRAGMA integrity_check`: `ok` — 문서 갱신 시 재확인
- `PRAGMA freelist_count`: `0`
- 입력 파일: 수정하지 않음

여기서 값 보존의 기준은 **44.719 MiB 입력 경량본**이다. 이전 단계에서 삭제한 `data_origin`이나 ` KST` 접미사를 복구한 것은 아니다. 값 보존은 테이블 제약·쓰기 동작·내부 rowid까지 같은 구조라는 뜻이 아니며, 조회 순서가 필요하면 명시적으로 `ORDER BY`를 사용해야 한다.

### 8.6 사용 방법과 조회 비용

일반 조회자는 딕셔너리를 직접 해석하지 않고 기존 이름의 뷰를 사용한다.

```sql
SELECT event_id, event_type, event_at
FROM event
LIMIT 100;
```

DB 도구에서는 `Tables` 아래의 `_data_*` 대신 `Views` 아래의 `event`, `search_result` 등을 열면 원래 문자열을 볼 수 있다.

| 항목 | 기존 44.719 MiB 파일 | 추가 14.297 MiB 파일 |
|---|---|---|
| 읽기 처리 | 저장한 값을 바로 읽음 | 사전·세션 조회 및 문자열 복원 연산 추가 |
| 디스크 읽기 | 상대적으로 큰 저장 공간 | 읽을 바이트가 줄어들 여지가 있음 |
| CPU 비용 | 복원 연산 없음 | 조회 열과 행 수에 따라 복원 비용 발생 |
| 필터·조인 | 원래 열을 대상으로 실행 | 복원 문자열 조건은 내부 키 인덱스 활용이 어려울 수 있음 |
| 직접 수정 | 실제 업무 테이블 수정 가능 | 기존 이름은 뷰이며 쓰기 트리거가 없어 직접 수정 불가 |
| 도구 탐색 | 업무 테이블 8개 | 물리 테이블·사전·뷰를 구분해야 함 |

현재 뷰에는 행별 사전·세션 조회가 포함되어 대량 조회 시 비용이 누적될 수 있다. DB 전체 크기가 작아져도 조회 결과 문자열의 크기까지 줄어드는 것은 아니다. 조회 시간·CPU·메모리 사용량은 비교 측정하지 않았으므로 성능 개선이나 추가 리소스가 없다고 보장하지 않는다.

여러 사람이 DB 도구에서 직접 열어 분석하는 배포본은 기존 44.719 MiB 파일을 권장한다. 추가 경량 테스트본은 저장 방식과 조회 성능을 검토하는 용도로만 사용한다. 전송 용량만 줄이는 목적이라면 기존 파일을 ZIP으로 전달하고 압축을 풀어 사용하는 방법이 구조를 이해하기 쉽다. 내부 데이터를 수정하려면 ID 형식, 사전 참조, 세션 공통값과 NULL 플래그를 함께 관리해야 한다.

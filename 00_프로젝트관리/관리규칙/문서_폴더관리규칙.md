- 최초 제정일: 2026-09-02 (KST)
- 최종 개정일: 2026-09-04 (KST)
- 적용 범위: 저장소의 공식 문서, 분석 산출물, 데이터, 발표자료, 교육과제 및 웹앱
- 문서 대장: `00_프로젝트관리/버전관리대장/문서_버전관리대장.md`
- 데이터 대장: `03_데이터모델링/데이터_버전관리대장.md`

## 1. 기본 원칙

1. 현재 `00~10` 번호 체계는 유지한다.
2. 사람이 관리하는 업무 폴더는 한글로 작성한다.
3. `.git`, `.github`, `app`, `tests`, `static`, `templates` 등 코드와 도구가 직접 참조하는 기술 경로는 변경하지 않는다.
4. 일반 산출물은 팀프로젝트, 개인과제, 제공자료로 구분하고 생성 연도와 월에 따라 보관한다.
5. 팀·개인 구분이 명확한 파일만 이동한다. 구분이 불명확하면 현재 위치를 유지하고 문서 대장에 `구분 확인 필요`로 기록한다.
6. 현행본은 업무 폴더에 두고 이전 버전은 같은 분류의 `이전버전/문서계열/`에 보관한다.
7. 파일 이동·이름 변경 후 관련 README, 코드 경로와 관리대장을 함께 갱신한다.
8. 임시 파일, QA 결과, 압축 해제 부산물과 개인정보 포함본은 Git에 추가하지 않는다.
9. `09_단계별 분석/`은 분석 실행 묶음의 연결성을 보존하기 위해 기존 폴더명과 내부 구조를 유지한다.

## 4. 팀·개인·제공자료 분류

- 파일명이나 본문에 `2팀`, `팀프로젝트`, `팀회의록`, `팀제출본`이 명확하면 팀프로젝트 또는 팀과제로 분류한다.
- `개인과제`, `개인실습`, `개인제출`이 명확하면 개인과제로 분류한다.
- 강의교안, 문제지, 빈 양식과 강사 제공 원본은 제공자료로 분류한다.
- 개인 이름만 있다는 이유로 개인과제로 추정하지 않는다.
- 동일 내용의 개인정보 포함본과 마스킹본이 있으면 마스킹본만 공식 현행본으로 관리한다.
- 판단 근거가 부족한 기존 파일은 이동하지 않는다.

## 5. 생성일 기준 보관

일반 산출물의 보관 월은 다음 순서로 판정한다.

1. 파일명에 포함된 `YYYYMMDD`
2. DOCX·PPTX·XLSX 내부 문서 생성일
3. Git에 최초로 추가된 커밋 날짜
4. 운영체제 파일 생성일
5. 신뢰할 수 있는 날짜가 없으면 현재 위치 유지

Windows 생성일은 복사, 다운로드, Git clone 과정에서 달라질 수 있으므로 단독 기준으로 사용하지 않는다. `09_단계별 분석/`은 `YYYY/MM` 이동 대상에서 제외한다.

## 6. 파일명 작성 규칙

일반 문서의 기본 형식은 다음과 같다.

```text
주제_문서종류_YYYYMMDD_vNN_상태_추가정보.확장자
```

예시:

```text
호텔검색_가설문서_20260902_v08_현행본_296건기준.docx
호텔검색_분석발표_20260903_v03_제출본.pptx
호텔검색_34일차실습답안_20260904_v01_제출본.docx
```

- 날짜는 8자리 `YYYYMMDD`, 버전은 두 자리 `vNN`을 사용한다.
- 상태는 `원본`, `양식`, `작업본`, `중간본`, `현행본`, `제출본`, `이전본`, `참고`, `비식별` 중 알맞은 값을 사용한다.
- `최종`, `진짜최종`, `완료2`, `복사본`, `(1)`, `(2)`, `final2`는 버전 표기로 사용하지 않는다.
- 파일명 날짜는 해당 버전의 생성일을 뜻하며 단순 이동만으로 변경하지 않는다.
- 개인 이름은 꼭 필요한 개인과제가 아니면 파일명에서 제외한다.
- 외부 원본의 출처 추적에 원래 이름이 필요하거나 코드가 직접 참조하면 변경하지 않을 수 있다.
- `README.md`, `.gitignore`, `requirements.txt` 등 표준 기술 파일명은 유지한다.
- `09_단계별 분석/`의 기존 실행 묶음 파일명은 코드·매니페스트 연결을 위해 유지한다.

## 7. 현행본과 이전 버전

1. 문서 대장에서 현재 기준 파일을 확인한다.
2. 동일 문서 계열의 버전 번호와 상태를 비교한다.
3. 확정된 현행본 한 개만 업무 폴더에 둔다.
4. 나머지는 `이전버전/문서계열/`에 보관한다.
5. 중복 여부가 불확실하면 삭제하지 않고 검토 대상으로 남긴다.
6. 내용이 완전히 같은 파일만 SHA-256 비교 후 하나로 정리한다.

## 8. 데이터 관리

- 현재 분석용 데이터는 `03_데이터모델링/현행데이터/`에서 사용한다.
- 이전 데이터 묶음은 `03_데이터모델링/이전버전/데이터셋/`에 보관한다.
- 원본 수집 파일은 `03_데이터모델링/원천데이터/`에 둔다.
- 같은 버전의 DB, CSV와 테이블 명세는 하나의 묶음으로 관리한다.
- 파일명, 행 수, SHA-256과 검증 결과는 `03_데이터모델링/데이터_버전관리대장.md`에 기록한다.
- 원본 데이터는 직접 덮어쓰지 않고 정제·마스킹·증강 결과를 새 버전으로 저장한다.

## 9. Git 제외 대상

- `로컬작업공간/`, `tmp/`, `upload/`, `outputs/`
- QA 렌더링 및 문서 압축 해제 부산물
- 임시 DB, 캐시, 개인 노트북 및 개인 식별정보 포함본
- 재생성 가능한 중간 산출물

예외적으로 `09_단계별 분석/` 실행 묶음에 포함된 코드, 데이터, 보고서, 검증 결과와 매니페스트는 해당 폴더 안에서 함께 관리한다.

## 10. 변경 및 검증 절차

1. `git status`로 수정·삭제·미추적 파일을 확인한다.
2. 파일의 주제, 소유 구분, 생성일, 버전과 상태를 확인한다.
3. 확실한 파일만 표준 경로로 이동하고 파일명을 정리한다.
4. 코드와 문서의 경로 참조를 수정한다.
5. 문서 대장과 데이터 대장을 갱신한다.
6. 이동 전후 파일 수와 중요 데이터의 SHA-256을 비교한다.
7. `git diff --check`와 필요한 실행 검증을 수행한다.
8. 원격 변경을 `git pull --ff-only`로 반영하고 충돌 여부를 다시 확인한다.

정리 작업의 최우선 원칙은 **확실한 파일만 이동하고, 애매한 파일은 그대로 유지하는 것**이다.

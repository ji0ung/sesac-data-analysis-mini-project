# 요구사항 변천과 현재 결정

## 1. 최초 기획

최초 문서는 Python FastAPI, SQLite, SQLAlchemy, Jinja2를 이용한 로컬 행동 로그 앱을 제안했다. USER, HOTEL, SEARCH, SEARCH_FILTER, EVENT, REVIEW, RESERVATION을 핵심으로 하고 검색→노출→상세→재검색→찜→예약 경로 복원을 목표로 했다.

## 2. 공개 운영 요구

이후 내부망·임시 터널이 아닌 누구나 링크로 접근하고 PC를 꺼도 한 달 이상 또는 지속적으로 사용할 수 있어야 한다는 요구가 추가됐다. 이에 현재 운영판은 Cloudflare 기반 Sites 공개 배포와 D1 영속 DB를 사용한다.

## 3. 검색 UX 확장

- Agoda, 호텔스컴바인, 여기어때와 유사한 검색·필터 구성
- 최초 화면은 최소 검색 조건만 유지
- 결과 옆 독립 스크롤 상세 옵션
- 검색 버튼과 옵션 적용 버튼을 눌러야 결과·로그 반영
- 한글 의미 검색, 지역 미선택 검색, 최대 가격 구간
- 세부지역과 호텔 상세 지역 표시
- 상세 옵션의 날짜·인원 변경은 최종적으로 금지

## 4. 호텔 상세·객실 확장

- 카드 전체 클릭으로 상세 이동
- 안내 중심 숙소 소개
- 호텔·객실 시설 구분
- 대표 리뷰 5개와 리뷰 점수·수
- 달력과 2026년 날짜별 일부 예약 불가
- 시설 이미지 8장 및 썸네일/화살표 탐색
- 실제 사진 API 검토 후 현재는 숙소 특성 기반 이미지 사용

## 5. 데이터 확장

- 5개 일본 도시
- 초기 50개에서 최종 지역별 200개, 총 1,000개
- 도시별 세부지역
- 호텔별 가상 대표 리뷰 5개
- 호텔명은 공개 실제 호텔 정보를 참고하되 나머지 값은 연구용 시뮬레이션

## 6. 실험 설계 확장

모든 오류를 항상 내는 방식이 아니라 세션·호텔·옵션 일부 조합에서만 스파, 발코니 등 선택 조건과 남은 객실 조건이 다르게 보이도록 했다. 검색어 의미에 맞는 결과 누락 또는 비관련 결과도 일부 추가했다.

초기 구현의 전체 기대 불일치 약 17.5%는 과도해 보일 수 있어 현재는 다음으로 보정했다.

- 정상 세션 75%, 오류 실험 세션 25%
- 객실 옵션 전체 기대 발생률 약 8%
- 키워드 검색 전체 기대 발생률 약 5%

이 값은 Agoda 공식 측정값이 아니다.

## 7. 사용자·관리자 요구

- 참여자 코드는 이름으로 대체
- 동일 이름은 동일 사용자
- 탭 종료 전까지 로그인 유지와 상태 표시
- 취소 시 이전 세션·화면 복귀
- 모든 핵심 데이터 콘솔 제공
- 테이블별 CSV
- 삭제·휴지통·복구
- 모바일 화면
- 기획 보고서 및 제작 자료 제공

## 8. 현재 정본

요구가 서로 충돌할 경우 가장 최근의 사용자 요구와 현재 작동하는 코드가 우선한다. 이 문서 묶음과 `public/staytrace-project-report.md`는 설명 자료이고, 구체적인 동작의 최종 정본은 배포된 코드와 DB migration이다.
